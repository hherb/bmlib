# Roadmap

This document tracks planned and implemented features for bmlib, grouped by
theme. Details of finished work stay brief — git history and `docs/plans/`
hold the full story.

| ✅ Done | A whole span beats a nested fragment | Issue #33 — `extract_json()` reduced an unfenced array of objects to its first element, dropping every sibling with no error, on a path both the Anthropic and OpenAI-compatible providers run for every `json_mode` response. The acceptance policy is now `_first_acceptable()`, run twice: whole spans first, the nested-object stage only when nothing at the top level parsed. Its non-dict fallback is *ranked* — a list holding an object beats any other non-dict span — because first-parseable would let an incidental `[]` be accepted by the first walk and substitute unrelated data that parses cleanly. `extract_and_repair_json()` gets no second walk: repairing a fragment fabricates structure the model never emitted. The same preference applies one layer up: `parse_json()` asks for whole spans only (`allow_fragments=False`), tries repair, and re-asks with fragments allowed only if repair also failed — a *truncated* array of objects never balances, so taking the fragment there dropped the sibling and skipped the repair that recovers the whole array (0.6.0) |

| ✅ Done | PubMed grants and author affiliations | Phase 2 row 11 of the bmlibrarian port — the last Phase 2 row. `fetch_pubmed` reads `<GrantList>` and `<AffiliationInfo>` into new `Grant` / `AuthorAffiliation` child rows, persisted in two new tables (`publication_grants`, `publication_affiliations`) on both backends and read back with `get_grants()` / `get_author_affiliations()`. Both tables carry a `source` column and storage is **replace-per-source**: a record's rows replace the stored rows for the source that asserted them and leave every other source's alone, so re-syncing PubMed cannot disturb what OpenAlex found — scoping by publication alone made the stored set depend on whichever source synced last, flip-flopping silently, and OpenAlex's API does carry funder data. `sync()` stamps the column from `record.source` so a fetcher cannot forget. Two upstream defects fixed with named regression tests: a grant naming neither agency nor award id was stored as a row identifying no award, and affiliations named their author "Smith John" against the author list's "Smith, John A". Upstream's `is_retracted` deliberately not ported — `publication_types` already carries "Retracted Publication", `retractions.py` answers authoritatively, and upstream reads RefType `RetractionOf` (this article *is* the notice) as retracted. Review additionally fixed three things the graft itself introduced: document prose is now escaped (``\ ` * ~ ^``, a set measured against 3,403 real fields — it alters 0.35% and removes every construct a CommonMark parser found, whereas `_` and `[`/`]` churned 4.3% and fixed nothing), since declaring a field Markdown without escaping corrupts `CYP2C19 (*1, *2, *3)` and lets "AUC ~ 0.80" pair with the `~2~` the fetcher emits; `<u>` is no longer mapped to `__x__`, which rendered underline identically to bold while asserting the source said "bold"; and a grant or affiliation naming no source now raises rather than landing in an unreachable bucket that no sync can ever replace — the `NOT NULL` column caught `None` but not the `""` the dataclass defaults to (0.8.0) |

| ✅ Done | A completed day is a durable claim | Issues #88, #89, #90, #91 — four ways a broken sync reported as a quiet day, all raised by the review of PR #87 and all with the same consequence: `sync()` writes `completed` to `download_days`, `_days_needing_fetch()` does not offer a past day again (with `recheck_days` at its default), and the records are permanently absent with nothing logged above INFO. **#88** — the three fetchers drove their page loops from the count their source gave them and never reconciled it against what arrived (reproduced: PubMed `Count=5000` with an error document served at HTTP 200 → `completed`, 0 records, 11 calls; OpenAlex `meta.count` 5,000 with one work and no `next_cursor` → `completed`, 1 record). One shared `fetchers/_reconcile.py` now applies three rules of different kinds: a *stalled* walk (a page delivering nothing while the count says records remain) is broken outright and carries no threshold — the only rule that catches a session expiring on the last page, so every fetcher must compute and pass it — *unreconcilable* delivery (records against no count at all) cannot be shown to have finished and so cannot complete, while nothing delivered against no count is the ordinary quiet day; and a naturally-ended short walk is judged against `SHORTFALL_FAILURE_RATIO = 0.5`, a smaller gap being logged at WARNING, completed, and returned as `FetchResult.note` into the new `SyncReport.notes`. The floor rather than strict inequality is load-bearing: a `failed` day is re-offered on *every* later run, so failing on a benign, permanent gap re-fetches that whole day for the rest of an installation's life. **The 0.5 is fixed before measurement**, unlike every other calibrated threshold in bmlib; #92 measures the per-source distribution and tightens it. Two supporting changes: each fetcher checks its envelope instead of reading it through `.get()` defaults (PubMed refuses a non-`PubmedArticleSet` root, carrying NCBI's own error text and stopping the walk rather than paging on; OpenAlex requires a list `results` and a `meta` with a numeric `count`; bioRxiv refuses a body carrying neither a `collection` key nor messages, deliberately *not* requiring a list `collection` — it reports a quiet day by omitting `total`, and whether it also omits `collection` is unmeasured, so #94 is the sampler that would let the guard be tightened), and PubMed reconciles *delivered elements* rather than parsed records, because `<PubmedBookArticle>` is delivered and deliberately skipped and counting parsed records would fail every day carrying a book chapter — forever; delivery counts the two record element names rather than every child, since `<DeleteCitation>` is legal and would mask a shortfall. **#89** — the status denylist becomes an allowlist on both the write and the read side, so a third-party fetcher's failure in any other spelling is no longer converted into a durable success, and the validated status is typed `DayStatus`. **#90** — any record that failed to store now fails its day and is named in `SyncReport.errors`; the broad per-record handler stays but logs the exception type, so a `TypeError` affecting every record does not read as bad data. **#91** — OpenAlex's `response.json()` moves inside its `try`, so a decode error is reported by the fetcher rather than by `sync()` as "Fetcher raised". 73 tests, one per reproduction row plus negative controls that a full walk, both possible bioRxiv quiet-day shapes and a day of book chapters still complete; every new guard verified by mutation. One accepted cost, chosen deliberately: a permanently-unstorable record pins its day into a retry on every run — loudly, where it used to be silently missing (unreleased) |
| ✅ Done | A day fetched before it ended is not durable | Issue #95, raised by the review of PR #93 and pre-existing — but the *likely* instance of the family, since it fires on every ordinary run rather than needing an API malfunction. `_days_needing_fetch()` re-offered `today` unconditionally and checked nothing about *when* a completed day had been fetched, so a day captured as today was stored `completed`, and tomorrow — neither `today` nor `failed` — it was never offered again at the default `recheck_days=0`. With the default window `[yesterday, today]`, a 09:00 cron durably lost whatever was indexed over the following 15 hours, and **no reconciliation rule can see it**: the source's own count agreed at 09:00, because the walk really did deliver everything that existed then. One rule replaces the special case — a completed day is durable only once it was fetched at or after **12:00 UTC on the following day**. The hour is not a safety margin, and that is the whole design: day *D* ends last in UTC−12, whose midnight is noon UTC on *D+1*, and that same instant is exactly the point beyond which "now" can no longer fall inside day *D* anywhere on earth — so the rule *subsumes* the `today` branch rather than approximating it, and day selection no longer consults the wall clock to decide whether a completed day is done (which is what makes it testable without faking the clock). Both cheaper rules are unsafe and not hypothetically: all three built-in sources are US-based (UTC−5 to UTC−8), so comparing UTC *dates* calls a fetch at 00:30 UTC on *D+1* durable while PubMed's own day *D* still has five hours to run, and comparing *local* dates is up to 15 hours out for a machine in Sydney. An unusable `downloaded_at` fails closed and warns — naive, unparseable and not-a-string are one answer, the naive case being the one that would otherwise raise `TypeError` from inside day selection and abort a whole sync, and not-a-string being what a change of the PostgreSQL DDL to a real timestamp type would produce (guarded from the other side on both backends). Costs exactly one extra fetch per day under the default window, which is the fix working; a window of three days or more run before 12:00 UTC pays one more. Deliberately **not** a fix for late *indexing* — `recheck_days` is what exists for that. 12 tests, every guard verified by mutation (unreleased) |
