# Roadmap

This document tracks planned and implemented features for bmlib, grouped by
theme. Details of finished work stay brief — git history and `docs/plans/`
hold the full story.

| Status | Feature | Details |

Needs signature-preserving block storage |
| ⬜ Planned | Embeddings beyond Ollama | Only Ollama implements `embed()`; add OpenAI and Gemini backends when a consumer needs them |
| ✅ Done | Consolidate JSON extraction | Issue #17 — one locator, `iter_json_spans()`, yields candidate spans in six priority stages without validating; `extract_json()` and `extract_and_repair_json()` are acceptance policies over it, dropping ~70 lines of duplicated fence and brace scanning. A fenced candidate outranks the object preference, and the repair path suppresses the nested-object stage so it cannot return a fragment of a span it rejected (0.6.0) |
| ✅ Done | A whole span beats a nested fragment | Issue #33 — `extract_json()` reduced an unfenced array of objects to its first element, dropping every sibling with no error, on a path both the Anthropic and OpenAI-compatible providers run for every `json_mode` response. The acceptance policy is now `_first_acceptable()`, run twice: whole spans first, the nested-object stage only when nothing at the top level parsed. Its non-dict fallback is *ranked* — a list holding an object beats any other non-dict span — because first-parseable would let an incidental `[]` be accepted by the first walk and substitute unrelated data that parses cleanly. `extract_and_repair_json()` gets no second walk: repairing a fragment fabricates structure the model never emitted. The same preference applies one layer up: `parse_json()` asks for whole spans only (`allow_fragments=False`), tries repair, and re-asks with fragments allowed only if repair also failed — a *truncated* array of objects never balances, so taking the fragment there dropped the sibling and skipped the repair that recovers the whole array (0.6.0) |
| ✅ Done | Field-level JSON salvage | `salvage_json_fields()` — when a long structured response is malformed in one place, recover the fields that are intact instead of losing all of it. Generalises biasbuster's `lenient_extract`; at most one repair pass per key, at the last match (0.6.0) |

| ✅ Done | Diagnosable JSON failures | `chat_json(retry_context=...)` labels every retry and failure message with the task; `parse_json()` warns when the repair stage was what rescued a response, since repair closes brackets and a truncated response can parse into a valid but incomplete object (0.6.0) |
| ✅ Done | `parse_json`'s return contract | Issue #33 — annotated `dict \| list`, which is what it always returned, and *enforced*: a bare scalar response now raises rather than slipping past an annotation that excludes it. Plus an opt-in `require_dict` that raises in `parse_json()` and retries inside `chat_json()` (fail-fast at temperature 0, mirroring truncation). `@overload` on `Literal[True]` keeps a real `dict` for strict callers, with a third `bool` variant so a runtime flag still type-checks. | **Context processing (`bmlib.context_processor`)** | | |
| ✅ Done | Hierarchical map-reduce over oversized content | Issue #49, Phase 1 item 2 of the bmlibrarian port — batch items to fit a context window, extract from each batch, feed the extractions back in and repeat until they fit. `IterativeContextProcessor` is the harness and carries no LLM dependency; `LLMChunkProcessor` runs extraction through a `BaseAgent`, accepting plain strings or `(text, score)` search results. `create_prisma_chunk_processor` deliberately not ported (application concept). PR #50's review closed a second round in the port itself: `progress_percent` could never leave 0.0, a query containing `{content}` had the batch spliced into it by two-pass substitution, a run that dropped every item reported "All batches failed" at a 1.0 success rate, the strict `FAIL` strategy was filed as an unexpected error with a traceback, `CONCATENATE` and `WEIGHTED` averaged confidence differently, per-run statistics on the instance made concurrent runs return each other's counts, the batch's index list was shared with the metadata and the result, and the package `__init__` imported the LLM stack the harness claims not to need (0.7.0) |

| ✅ Done | PubMed grants and author affiliations | Phase 2 row 11 of the bmlibrarian port — the last Phase 2 row. `fetch_pubmed` reads `<GrantList>` and `<AffiliationInfo>` into new `Grant` / `AuthorAffiliation` child rows, persisted in two new tables (`publication_grants`, `publication_affiliations`) on both backends and read back with `get_grants()` / `get_author_affiliations()`. Affiliations are one row per *(author, affiliation)* pair rather than upstream's nested grouping, and carry the author's `position` — first-author and senior-author affiliation are the COI signals, and the name alone cannot recover the ordering. Both tables carry a `source` column and storage is **replace-per-source**: a record's rows replace the stored rows for the source that asserted them and leave every other source's alone, so re-syncing PubMed cannot disturb what OpenAlex found — scoping by publication alone made the stored set depend on whichever source synced last, flip-flopping silently, and OpenAlex's API does carry funder data. `sync()` stamps the column from `record.source` so a fetcher cannot forget. No UNIQUE constraint on the natural key (wholly nullable; both backends treat NULL as distinct, so it would protect nothing while appearing to) and none is needed: exact repeats are collapsed at parse time, PubMed emitting a `<Grant>` block verbatim twice in 31 of 575 measured entries. `_consolidate_rows()` relocates the new child rows before deleting their parent — both backends enforce foreign keys, so a stranded row aborts the whole store; verified by mutation. Two upstream defects fixed with named regression tests: a grant naming neither agency nor award id was stored as a row identifying no award, and affiliations named their author "Smith John" against the author list's "Smith, John A". Upstream's `is_retracted` deliberately not ported — `publication_types` already carries "Retracted Publication", `retractions.py` answers authoritatively, and upstream reads RefType `RetractionOf` (this article *is* the notice) as retracted. Review additionally fixed three things the graft itself introduced: document prose is now escaped (``\ ` * ~ ^``, a set measured against 3,403 real fields — it alters 0.35% and removes every construct a CommonMark parser found, whereas `_` and `[`/`]` churned 4.3% and fixed nothing), since declaring a field Markdown without escaping corrupts `CYP2C19 (*1, *2, *3)` and lets "AUC ~ 0.80" pair with the `~2~` the fetcher emits; `<u>` is no longer mapped to `__x__`, which rendered underline identically to bold while asserting the source said "bold"; and a grant or affiliation naming no source now raises rather than landing in an unreachable bucket that no sync can ever replace — the `NOT NULL` column caught `None` but not the `""` the dataclass defaults to (0.8.0) |
| ✅ Done | PubMed titles and abstracts keep their markup | `_text()` reads `el.text` — the text before the first child — so any title carrying markup was truncated there, silently: `"Effects of H<sub>2</sub>O and <i>E. coli</i> on outcomes"` was stored as `"Effects of H"`. Titles and abstracts now go through a mixed-content walker mapping `b`/`i`/`sup`/`sub`/`u` to Markdown, and each `AbstractText` becomes a `**LABEL:** text` section separated by a blank line, with the label from `Label` *or* `NlmCategory` — reading only `Label` dropped the heading from every section labelled the other way. A second upstream defect fixed: stripping at every recursion level ate the space inside a formatted run (`**Randomised****trial**`), and leaving it in place is no better since CommonMark wants the delimiter adjacent to non-whitespace, so edge whitespace is re-emitted outside the markers. **Not comparable with stored values** — every synced title and abstract changes shape (0.8.0) |
| ✅ Done | Retraction Watch notices | Phase 2 row 10 of the bmlibrarian port. `parse_retraction_watch_csv()` streams the Crossref export into `RetractionNotice`s; `store_retraction_notices()` upserts them on Retraction Watch's own `record_id`, so re-importing the monthly file is idempotent; `lookup_retractions()` + the pure `is_retracted()` answer "is this paper retracted?". Not a fetcher — a notice annotates a paper that is usually not in the caller's table. Five upstream defects fixed, each with a named regression test: the PMID candidate list matched none of the export's real column names; the encoding-retry loop never cleared its accumulator, duplicating every row already read; `utf-8` was tried before `utf-8-sig`, so a BOM hid the first column; every row was stored as retracted, including Corrections, Expressions of Concern and Reinstatements; and missing identifiers are truthy sentinels (`0` in 46% of PubMed ID cells, `Unavailable`/`unavailable` in DOI cells), which a truthiness test accepts and which collapse tens of thousands of notices onto one key.
