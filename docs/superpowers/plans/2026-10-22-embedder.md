# Embedder (arctic-embed-l-v2.0, GGUF) Implementation Plan

> **Historical.** This is the plan as written before implementation. Where it differs from the code, the code and `docs/manual/embeddings.md` are right. Among the differences: `embed` is not in `all` and needs `llama-cpp-python>=0.3.36`; there is no `batch_tokens`, and Python turns flash attention on; the progress hooks return a bool and can cancel; the download uses its own `bmlib/{version}` User-Agent and a temporary file per call, not a shared `.part`; and `--verify-reference` is required by the converter.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** bmlib can embed text with snowflake-arctic-embed-l-v2.0 in-process, in Rust and in Python, from our own converted GGUF. The model is downloaded on first use and checked against a pinned checksum, and the output is 256-dimensional L2-normalised vectors that match the original model.

**Architecture:**
- **One model file, our own.** A committed script converts the Hugging Face model to GGUF (F16 and Q8_0) with llama.cpp at the commit the Rust binding vendors. It checks the result against reference vectors, and the files are published to `hherb/snowflake-arctic-embed-l-v2.0-gguf`.
- **Both languages share one model description.** Each language has the same small model description: repository, revision, file, size and sha256, held to a committed manifest. Each has a streaming download that verifies the checksum before the file lands.
- **The `Embedder`.** Rust uses `llama-cpp-2`; Python uses `llama-cpp-python`. Both use CLS pooling, take the first 256 dimensions and renormalise them, and add the `"query: "` prompt for queries only.
- **How parity is held.** Pure behaviour goes through a hand-written contract fixture. Model behaviour goes through a live, gated test against reference vectors from the original model (sentence-transformers, fp32), with a stated cosine tolerance.

**Tech Stack:** llama.cpp `26394b4e6749a41c3633db040e0987500a5f7013`; Rust `llama-cpp-2 = "=0.1.159"` and `sha2 0.10` (both optional), plus `ureq` 3 (existing); Python `llama-cpp-python` (optional extra), `hashlib` and `urllib` (stdlib); the `hf` CLI for the upload.

## Review Focus

1. **An interrupted or corrupted download** (connection drop mid-body, wrong bytes, disk full) never leaves a file at the final path. The partial `.part` file is removed or overwritten on the next try, and a checksum mismatch is an error. *Pinned by `download_truncated_body_leaves_no_model` and `download_wrong_bytes_is_checksum_error` (Tasks 4 and 6).*
2. **A file already at the final path that does not match** (replaced or truncated by hand) is not trusted. `download_model` re-fetches it, and `verify_model` reports the mismatch. *Pinned by `existing_mismatched_file_is_refetched` (Tasks 4 and 6).*
3. **A text longer than 8 192 tokens** is an error naming its index, never silently cut. `llama-cpp-python`'s `embed()` truncates by default, so call it with `truncate=False` and pre-check token counts. *Pinned by the live tests `overlong_text_is_an_error` (Tasks 5 and 7).*
4. **Empty or whitespace-only texts** are rejected before the model runs, by the pure `check_texts`. *Pinned by contract cases (Tasks 4 and 6).*
5. **Query/document asymmetry.** `embed_query(q)` must equal `embed_documents([QUERY_PREFIX + q])[0]`. A document that happens to start with `"query: "` is not changed. *Pinned by the contract `query_text` cases and the live tests `query_is_prefixed_document` (Tasks 5 and 7).*

### Task 2: The conversion script

**Files:**
- Create: `scripts/convert_embedding_model.py`
- Create: `tests/test_convert_embedding_model.py`

**Interfaces:**
- Produces, as pure functions in the script (importable for tests through `importlib`):
  - `sha256_file(path: Path) -> str`, which streams the file in 1 MiB blocks.
  - `manifest(files: list[Path], llama_cpp_commit: str, base_revision: str) -> dict`, shaped as `{"base_model", "base_revision", "llama_cpp_commit", "files": [{"file", "size", "sha256"}]}`.
  - `model_card(manifest: dict) -> str`.
- The CLI: `--llama-cpp <checkout> --base-dir <HF snapshot dir> --out <dir> [--verify-reference tests/fixtures/embedding_reference.json]`.

What the script does:
1. It asserts that `git -C <checkout> rev-parse HEAD` equals `26394b4e6749a41c3633db040e0987500a5f7013`, and refuses otherwise.
2. It runs `python <checkout>/convert_hf_to_gguf.py <base-dir> --outtype f16 --outfile <out>/snowflake-arctic-embed-l-v2.0-F16.gguf`.
3. It runs `<checkout>/build/bin/llama-quantize <F16> <out>/snowflake-arctic-embed-l-v2.0-Q8_0.gguf Q8_0`.
4. With `--verify-reference`, it embeds each reference item using `<checkout>/build/bin/llama-embedding -m <gguf> --pooling cls --embd-normalize -1 --embd-output-format json -p <text>` (query items get `query: ` prepended). It truncates and renormalises to 256 dimensions and fails unless every cosine meets the Global Constraints tolerance for that file.
5. It writes `manifest.json` and `README.md` into `--out`.

The model card is YAML front matter followed by Markdown:
- **Front matter:**
  - `license: apache-2.0`
  - `base_model: Snowflake/snowflake-arctic-embed-l-v2.0`
  - `base_model_relation: quantized`
  - `library_name: llama.cpp`
  - `tags: [gguf, sentence-similarity, feature-extraction]`
  - `pipeline_tag: sentence-similarity`
- **Body sections:**
  - What this is, with attribution to Snowflake.
  - The files table (file, size, sha256).
  - How it was made (the llama.cpp commit and the exact two commands).
  - Usage: CLS pooling, `"query: "` for queries, first 256 dimensions renormalised, 8 192-token context.
  - The verification result: minimum cosine per file against the fp32 reference.
  - Licence: Apache-2.0, unchanged from the base model.

`download_model` behaviour:
1. If `directory / model.file` exists and verifies, return it with no network.
2. Otherwise stream `model.url()` with `urllib.request` (bmlib's User-Agent from `bmlib._user_agent`) in 1 MiB blocks into `<file>.part`, hashing as it writes and calling `progress(done, model.size)`.
3. On completion, check size and sha256. On success, `os.replace` the `.part` file to the final path. On any failure, delete the `.part` file and raise.
4. A mismatched file at the final path is deleted before the fetch.
